# supply-chain-risk-radar

## Contexte
Radar de risque supply chain. Ingère GDELT 2.0 (toutes les 15 min), stocke dans un lakehouse Apache Iceberg (bronze/silver/gold), classe les événements avec un LLM, calcule un score de risque 0-100 pour 100 fournisseurs d'une « Entreprise démo ».

Deux sorties :
- (a) pipeline local complet : Kafka + Spark Structured Streaming + Iceberg + dbt + Dagster.
- (b) démo en ligne « live-lite » : GitHub Actions toutes les 30 min -> tables gold en Parquet -> site statique React lisant avec DuckDB-WASM.

Environnement : WSL2 Ubuntu 24.04, Python 3.11 (venv), Docker. pyspark 4.1.1 déjà utilisé sur un autre projet.
Rôle de Claude : mentor senior data engineer, réponses en français, expliquer le pourquoi de chaque choix.

## Règles non négociables
1. Aucune donnée inventée. Seul le portefeuille fournisseurs est fictif (graine fixe, étiqueté « Entreprise démo »). Tout événement ou chiffre de trafic vient d'un fichier réellement téléchargé, avec URL source et horodatage en bronze.
2. Avant d'ajouter une dépendance Spark/Iceberg : vérifier sa compatibilité exacte avec Spark 4.1.x sur Maven Central, dire ce qui a été vérifié. Si non confirmé, proposer une alternative.
3. Aucun service cloud payant ni clé d'API LLM utilisée sans confirmation de l'utilisateur.
4. Tests pytest pour chaque transformation.

5. Messages de commit et descriptions de PR : aucune ligne « Co-Authored-By: Claude » ni mention « Generated with Claude Code ». Le réglage `attribution` de `.claude/settings.json` les désactive aussi côté outil.

6. Toute anomalie remarquée (écart, valeur inattendue, comportement non documenté) est signalée à l'utilisateur immédiatement, sans attendre la fin de l'étape ni la juger sans importance.

Méthode : une étape à la fois, arrêt après chaque étape pour validation.

Tâches différées (échéances et raisons) : voir [docs/backlog.md](docs/backlog.md).

## Plan des phases
- Phase 0 — Fondations locales : scaffold, infra docker (Kafka KRaft, MinIO, catalogue Iceberg REST), producteur GDELT, streaming vers bronze.
- Phase 1 — Bronze/silver : parsing et typage, déduplication, référentiel des détroits (IMF PortWatch écarté, table « mentions » reportée en phase 3, voir Décisions).
- Phase 2 — Portefeuille et gold : générateur des 100 fournisseurs (graine fixe), dbt, modèles gold, score de risque 0-100. Le terme « trafic maritime » est remplacé par « événements GDELT près d'un détroit de la route du fournisseur » (référentiel `silver.ref_chokepoints`). Étapes : 1 portefeuille, 2 jointure géographique, 2b chargement historique GDELT (60 derniers jours + février-mars 2026), 3 score v1 en gold.
- Phase 3 — Classification par règles (CAMEO), sans LLM ni clé d'API (décision du 2026-10-10) : familles d'événements pertinentes pour la supply chain, règles documentées et mesurées. Cas de démo : Ormuz, février-mars 2026, avec l'historique GDELT de cette période. « LLM local via Ollama, limité aux événements des alertes affichées » : v2, au backlog. Table GDELT « mentions » (bronze/silver) au backlog.
- Phase 4 — Orchestration : assets Dagster, planification 15 min, sensors, reprise sur incident.
- Phase 5 — Live-lite : export gold en Parquet, GitHub Actions 30 min, site React + DuckDB-WASM, API éventuelle.
- Phase 6 — Durcissement : qualité des données, observabilité, CI, documentation, préparation entretien.

- 2026-10-08 — Renommage `slot_ts` -> `gdelt_batch_label_ts` (manifeste, en-tête Kafka) et `src_slot_ts` -> `src_gdelt_batch_label_ts` (bronze, le préfixe `src_` des colonnes de lignage est conservé), et « créneau » -> « lot GDELT » partout. Raison : « slot » laissait croire à une heure de publication, alors que c'est l'étiquette du lot. Appliqué aux tables existantes par `ALTER TABLE ... Le bronze lit aussi l'ancien en-tête Kafka `slot_ts` (messages publiés avant le renommage, rétention 7 jours) ; à retirer à partir du 2026-10-16.

- 2026-10-09 — Silver `silver.gdelt_events`, code dans `silver/` (job batch Spark ; `transform/` est réservé à dbt). Lecture incrémentale par filtre `ingested_at > curseur`, curseur en propriété de la table silver (`scrr.bronze_ingested_at_cursor_us`, microsecondes), mis à jour après les MERGE. Comparée à la lecture incrémentale par snapshots Iceberg (`start-snapshot-id`) : le filtre est retenu parce qu'il survit à l'expiration des snapshots et à la compaction prévues en phase 4 (l'incrémental par snapshots échoue si le snapshot de départ a expiré), se rejoue à la main par simple date, se lit tel quel depuis DuckDB/dbt et profite du partitionnement `days(ingested_at)`. Condition : `ingested_at` croît avec les commits, vrai tant qu'un seul job écrit le bronze ; vérifié sur les 8 snapshots du bronze (le max de `ingested_at` croît strictement et précède le commit de 1 à 14 s). Si un second écrivain apparaît, revoir ce choix. Idempotence : interrompu avant la mise à jour du curseur, le job rejoue la même fenêtre et les MERGE n'insèrent rien (testé).
- 2026-10-09 — Typage strict de la silver : tout champ non vide qui n'est pas du type attendu, ou hors plage (lat [-90, 90], long [-180, 180], GoldsteinScale [-10, 10], QuadClass 1-4, types géographiques 0-5, AvgTone [-100, 100], compteurs entiers >= 0), met la ligne en quarantaine avec la raison (`silver.gdelt_events_quarantine`, ligne brute et lignage conservés). Seule l'absence est normalisée : chaîne vide -> NULL pour les colonnes facultatives (en GDELT, vide = non renseigné), et quarantaine pour les obligatoires. Codes CAMEO gardés en texte (zéros de tête). Ligne à `field_count != 61` : quarantaine sans tentative de typage. Les plages sont des choix de ma part (le codebook ne les garantit pas toutes) : à ajuster si une ligne réelle valide est rejetée.
- 2026-10-09 — Dédoublonnage silver : le premier arrivé gagne (ordre `ingested_at`, partition, offset), `MERGE INTO ... WHEN NOT MATCHED THEN INSERT *` sans clause UPDATE. Raison : un événement GDELT est un fait, le producteur « au moins une fois » ne fait que le répéter ; une mise à jour silencieuse changerait l'historique. `row_hash` (sha256 de la ligne brute) permet de compter les « doublons » au contenu différent, signalés dans les statistiques du passage. Partition `days(date_added)`.
- 2026-10-09 — Premier passage sur les données réelles (65 lots GDELT, 76 427 lignes bronze) : 76 427 lignes en silver, 0 quarantaine, 0 doublon, 0 conflit, 1 snapshot, 34 s. Chaque ligne bronze retrouvée en silver (coordonnées Kafka), second passage = no-op. Les chemins quarantaine et doublons ne sont donc exercés que par les tests, pas encore par des données réelles. ActionGeo exploitable (latitude et longitude présentes, type de lieu > 0, pas (0, 0)) : 74 263 / 76 427 = 97,17 %. Les 2 164 restants : 2 162 de type 0 (aucun lieu), 2 de type pays sans coordonnées. 25 événements ont une paire de coordonnées incomplète (latitude vide, longitude « 42 », pays « GG ») : conservés tels quels, jamais exploitables.
- 2026-10-09 — Port hôte par défaut du catalogue REST : 18181 (au lieu de 8181), cohérent avec Kafka 19092 et MinIO 19000/19001, et hors de la plage 8178-8277 que Windows réserve après un redémarrage. Le port interne du conteneur reste 8181. Le `.env` local de contournement est supprimé. Reste surchargeable par `ICEBERG_REST_PORT`.
- 2026-10-09 — Curseur de la silver confirmé : c'est le `max(ingested_at)` des lignes réellement lues (jamais l'heure d'exécution), calculé sur la fenêtre figée du passage. Un lot bronze commité pendant le passage a un `ingested_at` plus récent que le curseur et sera lu au passage suivant (testé en en commitant un entre la lecture et la mise à jour du curseur). Limite du test : il écrit dans la même session Spark, qui invalide alors son cache et relit le lot tardif dès le premier passage ; l'invariant (le curseur ne dépasse jamais ce qui a été lu) tient dans les deux cas, et le MERGE n'insère pas deux fois.
- 2026-10-09 — `ops.pipeline_runs` (Iceberg, `lakehouse.ops`) : une ligne par exécution du silver, réussie ou échouée (statut, erreur, durée mesurée à l'horloge monotone, lignes lues / insérées / en quarantaine, doublons, doublons au contenu différent, % ActionGeo exploitable sur les lignes lues pendant l'exécution, curseur avant et après). Colonnes génériques pour les jobs suivants. Un passage sans rien de neuf écrit quand même une ligne (pourcentage NULL). Pas de reconstitution des passages antérieurs au 2026-10-09 : le premier passage complet (76 427 lignes) n'y figure pas, ses chiffres sont dans cette page. Une ligne de plus tous les quarts d'heure à terme : table à compacter en phase 4 avec les autres.
