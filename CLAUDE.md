# supply-chain-risk-radar

## Contexte
Radar de risque supply chain. Ingère GDELT 2.0 (toutes les 15 min), stocke dans un lakehouse Apache Iceberg (bronze/silver/gold), classe les événements avec un LLM, calcule un score de risque 0-100 pour 100 fournisseurs d'une « Entreprise démo ».

Deux sorties :
- (a) pipeline local complet : Kafka + Spark Structured Streaming + Iceberg + dbt + Dagster.
- (b) démo en ligne « live-lite » : GitHub Actions toutes les 30 min -> tables gold en Parquet -> site statique React lisant avec DuckDB-WASM.

Environnement : WSL2 Ubuntu 24.04, Python 3.11 (venv), Docker. pyspark 4.1.1 déjà utilisé sur un autre projet.
Rôle de Claude : mentor senior data engineer, réponses en français, expliquer le pourquoi de chaque choix.

## Règles non négociables
1. Aucune donnée inventée. Seul le portefeuille fournisseurs est fictif (graine fixe, étiqueté « Entreprise démo »). Tout événement ou chiffre de trafic vient d'un fichier réellement téléchargé, avec URL source et horodatage en bronze.
2. Avant d'ajouter une dépendance Spark/Iceberg : vérifier sa compatibilité exacte avec Spark 4.1.x sur Maven Central, dire ce qui a été vérifié. Si non confirmé, proposer une alternative.
3. Aucun service cloud payant ni clé d'API LLM utilisée sans confirmation de l'utilisateur.
4. Tests pytest pour chaque transformation.

5. Messages de commit et descriptions de PR : aucune ligne « Co-Authored-By: Claude » ni mention « Generated with Claude Code ». Le réglage `attribution` de `.claude/settings.json` les désactive aussi côté outil.

6. Toute anomalie remarquée (écart, valeur inattendue, comportement non documenté) est signalée à l'utilisateur immédiatement, sans attendre la fin de l'étape ni la juger sans importance.

Méthode : une étape à la fois, arrêt après chaque étape pour validation.

Tâches différées (échéances et raisons) : voir [docs/backlog.md](docs/backlog.md).

## Plan des phases
- Phase 0 — Fondations locales : scaffold, infra docker (Kafka KRaft, MinIO, catalogue Iceberg REST), producteur GDELT, streaming vers bronze.
- Phase 1 — Bronze/silver : parsing et typage, déduplication, référentiel des détroits (IMF PortWatch écarté, table « mentions » reportée en phase 3, voir Décisions).
- Phase 2 — Portefeuille et gold : générateur des 100 fournisseurs (graine fixe), dbt, modèles gold, score de risque 0-100. Le terme « trafic maritime » est remplacé par « événements GDELT près d'un détroit de la route du fournisseur » (référentiel `silver.ref_chokepoints`).
- Phase 3 — Classification LLM : taxonomie d'événements, évaluation sur échantillon, coûts (accord préalable obligatoire). Cas de démo : Ormuz, février-mars 2026, avec l'historique GDELT de cette période. Table GDELT « mentions » (bronze/silver) pour que le LLM résume à partir de plusieurs articles.
- Phase 4 — Orchestration : assets Dagster, planification 15 min, sensors, reprise sur incident.
- Phase 5 — Live-lite : export gold en Parquet, GitHub Actions 30 min, site React + DuckDB-WASM, API éventuelle.
- Phase 6 — Durcissement : qualité des données, observabilité, CI, documentation, préparation entretien.

Lecture incrémentale par filtre `ingested_at > curseur`, curseur en propriété de la table silver (`scrr.bronze_ingested_at_cursor_us`, microsecondes), mis à jour après les MERGE. Comparée à la lecture incrémentale par snapshots Iceberg (`start-snapshot-id`) : le filtre est retenu parce qu'il survit à l'expiration des snapshots et à la compaction prévues en phase 4 (l'incrémental par snapshots échoue si le snapshot de départ a expiré), se rejoue à la main par simple date, se lit tel quel depuis DuckDB/dbt et profite du partitionnement `days(ingested_at)`. - 2026-10-09 — Typage strict de la silver : tout champ non vide qui n'est pas du type attendu, ou hors plage (lat [-90, 90], long [-180, 180], GoldsteinScale [-10, 10], QuadClass 1-4, types géographiques 0-5, AvgTone [-100, 100], compteurs entiers >= 0), met la ligne en quarantaine avec la raison (`silver.gdelt_events_quarantine`, ligne brute et lignage conservés). Seule l'absence est normalisée : chaîne vide -> NULL pour les colonnes facultatives (en GDELT, vide = non renseigné), et quarantaine pour les obligatoires. Codes CAMEO gardés en texte (zéros de tête). Ligne à `field_count != 61` : quarantaine sans tentative de typage. Les plages sont des choix de ma part (le codebook ne les garantit pas toutes) : à ajuster si une ligne réelle valide est rejetée.

Raison : un événement GDELT est un fait, le producteur « au moins une fois » ne fait que le répéter ; une mise à jour silencieuse changerait l'historique. `row_hash` (sha256 de la ligne brute) permet de compter les « doublons » au contenu différent, signalés dans les statistiques du passage. Un lot bronze commité pendant le passage a un `ingested_at` plus récent que le curseur et sera lu au passage suivant (testé en en commitant un entre la lecture et la mise à jour du curseur).
